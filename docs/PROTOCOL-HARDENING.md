# 通讯"不被逆向"怎么做（协议加固方案）

> 针对审计 **M3** 与 v1.4.2 的如实边界：*"拿到一个样本 ≈ 拿到协议层身份"*。
> 本文只讲**可落地的设计**与**可验证的验收**，不讲"加壳/混淆"这类心理安慰。

---

## 0. 先拆成三个不同的问题（混在一起就会做错）

| 编号 | 问题 | 攻击者拿到什么 | 现在（≤ v1.4.2） |
|---|---|---|---|
| **A** | **静态逆向**：从 exe 里掏出密钥/协议 | 一个载荷文件 | ❌ 输。全局 PSK 烘在二进制里，配置块只有 4 字节 XOR |
| **B** | **被动解密**：抓包解出内容 | 一段流量 + （可能）一个样本 | ❌ 输。用 A 拿到的全局 key 就能解 |
| **C** | **主动冒充/重放**：冒充服务端或植入端 | 密钥 + 网络位置 | ❌ 输。无每植入端身份、无重放防护、植入端 TLS 不校验证书 |

> 关键结论：**A 是"能不能掏出来"，B/C 是"掏出来之后能干什么"。**
> 加固的正确顺序是：**先让"掏出来也没用"（把 A 的收益归零），再谈让 A 更难（混淆）。**
> 反过来说，只做混淆（garble/加壳/虚拟化）而不改密钥模型 = 把门锁换成更花的锁，钥匙还挂在门上。

---

## 1. 目标模型（一句话）

> **二进制里没有任何"能解密别人"的长期密钥；每次上线协商出只属于这一次会话的密钥；每一帧都绑定"谁、哪条任务、第几帧"。**

四条机制就够了，缺一条就破一个方向：

1. **每植入端独立密钥**（解决 A、B 的横向扩散）
2. **会话级前向保密**（解决 B 的长期解密：抓包 + 事后拿到私钥也解不开旧流量）
3. **帧级绑定与防重放**（解决 C 的伪造/重放）
4. **帧版本号 + 密钥轮换/吊销**（解决工程化：老载荷共存、单点作废）

---

## 2. 具体设计

### 2.1 L1 每植入端身份：`sealed box` + ECDH

**构建时**（服务端做）：
1. 服务端持有一对**长期**密钥：`SrvPub`/`SrvPriv`（X25519 或 Ed25519+曲线，SrvPriv **不烘进任何载荷**、离线保存或放 KMS）。
2. 为本次载荷生成 `ImplantPub`/`ImplantPriv`（X25519 临时对）。
3. 用 `SrvPub` 对 `ImplantPriv` 做**密封封装**（`crypto_box_seal` / ECIES：临时 ECDH + AEAD），得到 `SealedImplantKey`。
4. 配置块里只放 `{key_id, ImplantPub, SealedImplantKey}`，**不含任何明文私钥**。

**上线时**：
5. 植入端用自己的 `ImplantPriv`……等等 —— 它自己也没有私钥。正确姿势有两种，选一种：
   - **方案 α（推荐、简单）**：不改这一步。植入端把 `SealedImplantKey` 原样发回（加密握手第一帧），服务端用 `SrvPriv` 解封得到 `ImplantPriv`，之后双方用它做 ECDH。**效果**：逆向者拿到样本只有"被封装的私钥"，没有 `SrvPriv` 解不开；即便解开，也只影响这一台。
   - **方案 β（更彻底）**：构建时把 `ImplantPriv` 用**机器无关的口令派生密钥**加密（如 `KDF(server 下发的一次性注册码)`），首次上线时换出。复杂度高，收益边际。
6. 双方做 `ECDH(ImplantPriv, SrvEphemeralPub)` 与 `ECDH(SrvPriv, ImplantPub)` 混合（HKDF）→ **会话密钥 `SK`**。会话结束即丢弃 → **前向保密**。

> 验收 A：从 3 个不同载荷里各掏出 `SealedImplantKey`，**互相解不开**、也解不开任何会话。
> 验收 B：抓 1 小时流量 + 事后拿到 `SrvPriv`，**仍解不开历史会话**（ECDH 临时量已丢）。

**服务端存储**：`key_id → {implant_pub, 状态(active/revoked), 构建时间, 会话数}`。删库/吊销单台不影响其它。

### 2.2 L2 帧绑定 + 防重放

现有帧是 `[4B len][1B type][AEAD(payload)]`。改造：

- AEAD 的 **AAD** 绑定上下文：`AAD = version || session_id || msg_type || seq || task_id(若有)`。
  → 把 A 会话的帧搬到 B 会话（或改 msg_type 冒充）在**认证阶段**就失败。
- 头部明文加 **`seq`（per-session 单调递增 u64）** 与 **`version`（帧协议版本）**。
- 服务端每会话维护**滑动窗口**（例如 64 宽）：`seq` 重复或落后窗口 → 直接丢并计数（`replay_dropped`）；跳变超过窗口 → 要求重新协商。
- `task_id` 绑定：结果帧必须带匹配的 `session_id + task_id`（v1.4.2 已在服务端做了归属校验，这里是协议层再做一次，防"服务端逻辑被绕过"）。

> 验收 C：把一帧原样重放 → 拒绝且计数 +1；把 A 的帧头 `session_id` 改成 B → 认证失败；把 `task_id` 改成别人的 → 拒绝。

### 2.3 L3 配置块不再"可逆混淆"

现状：`server_url` / `encryption_key` 用**每构建 4 字节 XOR**，密钥也在二进制里 → 等于明文。

改为：配置块用 **`SK_cfg`（每构建随机 32B）** 加密（AEAD），`SK_cfg` 本身用 `SrvPub` 密封（§2.1）。植入端启动时把 `SealedCfgKey` 发回，由服务端解封后下发 `SK_cfg`？—— 那启动前无法读 `server_url`，形成"先有鸡还是蛋"。

两种可落地的折中：

| 方案 | 二进制里留下什么 | 逆向者能拿到什么 | 代价 |
|---|---|---|---|
| **α 最小可用** | `server_url` 明文（或仅域名）、`SealedCfgKey` | 回连地址；**拿不到协议密钥** | 地址暴露（本来也会被抓包看到） |
| **β 地址也藏** | 只有 `SealedCfgKey` + 一组**诱饵地址**，真实地址由服务端在握手后下发 | 地址需服务端授权才能拿到 | 首帧需要"先连服务端"（可用 CDN/固定域名兜底） |

> 建议：**先做 α**（去掉最致命的"协议密钥可逆"），β 作为后续。

### 2.4 L4 传输层：把 `InsecureSkipVerify` 换掉

现状：植入端 TLS 全 `InsecureSkipVerify`（审计 L1）—— 应用层 AEAD 挡住了内容伪造，但丢了"对端是哪台服务器"的判定，配合共享 PSK 就等于可以 MITM 观察。

- **证书固定（pin）**：构建时把服务端证书的 **SPKI SHA-256** 烘进配置块，握手时比对；自签证书也能安全用（pin 的是公钥不是 CA）。
- 或 `ca_file` 内嵌（自签 CA），配合 `verify_hostname`。
- 有公信 cert 的部署，`pin` 仍建议保留（防运营商/企业 CA 中间人）。

> 验收：把服务端证书换成另一张同域名证书 → 植入端拒绝连接（不是静默重连）。

### 2.5 L5 流量形态（"看不出是 C2"不是本文重点，但列出来）

- **长度归一**：帧填充到固定桶（如 512/1024/4096），避免"命令输出长短"泄露动作类型；
- **节奏**：心跳已带抖动；再叠加"空闲期偶发噪声帧"与"批量任务错峰"；
- **应用层伪装**：HTTP 通道用真实站点的 `Content-Type`/路径形状（已有 `mimicry`）；HTTP/2 + uTLS/JA3（已在 full 档，缺抓包验证）；域前置 + CDN（需外部材料）。

> 这一层只影响"被怀疑"，不影响"被解密"。**先做 §2.1~2.4，再做这层。**

### 2.6 L6 生命周期（工程化，别忽略）

- **`key_id` 与帧版本**：服务端同时支持 v1（共享 PSK）与 v2（每植入端），按帧 `version` 分派 → **老载荷不炸**。
- **吊销**：`key_id` 标 `revoked` → 该植入端后续连接被拒（但已建立的会话怎么办？策略选项：立即断 / 允许到心跳超时）。
- **轮换**：`SrvPriv` 轮换时，旧 `key_id` 用旧私钥验，新载荷用新私钥 → 需要保留一份"私钥环"。
- **私钥存放**：`SrvPriv` 不进 `server.yaml`（会被 H3 那类漏洞读走）；放独立文件（0600）或 KMS，启动时加载到内存。

## 3. 为什么这样"逆向也没用"（威胁模型推导）

| 逆向者做到什么 | v1.4.2 现在能拿到 | 做完 §2.1~2.3 后能拿到 |
|---|---|---|
| 反编译出一个样本 | **全局 AES key** → 解所有流量、冒充服务端 | 只有 `ImplantPub` + `SealedImplantKey`（无 `SrvPriv` 解不开） |
| 抓 1 小时流量 | 用上面的 key **全解** | 只有 AEAD 密文；会话密钥是 ECDH 临时产物、已随会话丢弃 |
| 拿到服务端磁盘（假设） | 一切 | 拿到 `SrvPriv` → 只能解**未来**会话；**历史会话仍解不开**（前向保密） |
| 重放一帧 / 改 `session_id` | 可能成功（无 seq/AAD 绑定） | 拒绝（AAD + 滑动窗口） |
| 拿手机器人样本，冒充服务端 | 用同一把 key 就能骗植入端 | 需要 `SrvPriv`（不在二进制里）；且有证书 pin |

**结论**：把"密钥"从"二进制里的常量"变成"服务端短时授权 + 每会话临时量"之后，
逆向的收益从"拿到整个 C2 的协议身份"降级为"理解了协议格式" —— 后者是**无法避免也无法阻止**的
（协议总有一天会被读出来），但它**不再等价于身份**。

## 4. 验收标准（可测，别写成"感觉更安全了"）

1. **样本互不通用**：构建 3 个载荷，用脚本从各自配置块提取 `SealedImplantKey`，
   断言 ①互相解不开 ②用任一载荷的会话密钥解其它两个的抓包 → 全部失败。
2. **前向保密**：抓一段会话流量 → 重启服务端并删掉该会话状态 → 用 `SrvPriv` 重放解密 → 失败。
3. **重放拒绝**：抓一帧原样重发 → 服务端拒绝且 `replay_dropped` 计数 +1；
   把 A 的帧 `session_id` 改成 B → 认证失败；改 `task_id` → 拒绝。
4. **证书 pin**：换一张同域名但不同公钥的证书 → 植入端**拒绝连接**（日志给出 `pin mismatch`）。
5. **兼容**：v1 载荷（共享 PSK）与 v2 载荷（每植入端）能同时在线，互不影响。

> 上面 5 条都能写进 `scripts/e2e_smoke.ps1` 的"安全回归"段，CI 里跑 1/3/5（2/4 需要真机与证书）。

## 5. 成本与顺序（v1.5 建议）

| 阶段 | 做什么 | 预估 | 风险 |
|---|---|---|---|
| **S1** | L1 每植入端密钥 + L2 帧版本/AAD/seq | 1.5~2 周 | 协议改动最大；**必须**双栈（v1 共存）避免老载荷失联 |
| **S2** | L3 配置块密封（方案 α）+ L4 证书 pin | 3~5 天 | pin 写错会连不上，需要"pin 校验失败也允许一次备用证书"的运维旋钮 |
| **S3** | 滑动窗口/回放计数上 UI + 吊销/轮换 | 3~5 天 | 吊销策略要定：立即断还是等超时 |
| **S4** | L5 长度归一/噪声帧 + HTTP/2 + JA3 抓包验证 | 1~2 周 | 收益是"少被怀疑"，非"不可解密" |

**不做**：
- 🚫 不自创密码学（用 X25519 + HKDF + AES-256-GCM / ChaCha20-Poly1305，标准组合）。
- 🚫 不把"抗逆向"寄托在 garble/加壳上（它只提高成本，不改变收益结构）。
- 🚫 不承诺"绝对不可逆向" —— 协议格式迟早会被读出来；我们的目标是**读了也没用**。

## 6. 参考实现（vshell）的密钥模型：同一个坑，而且更深

被问到"vshell 不也是自己设一个固定密钥吗"——**是，而且更糟**。代码在本地 `vshell/`（未跟踪），证据：

| 维度 | vshell 做法 | 出处 |
|---|---|---|
| 密钥来源 | **面板手填的「流量加密盐」**，构建时 `-X main.EncryptSalt=…` 注入载荷 | `c2engine/builder.go:153-154`、`:260-266` |
| 默认值 | **字面量 `"default"`**（`VerifyKey` 也是 `"default"`） | `builder.go:153-154` |
| 消息帧密钥 | `hex(md5(salt))` → 32 个 ASCII 字符直接当 AES-256 密钥（**MD5 当 KDF**） | `protocol.go:167-200`、`message_key_derivation_test.go:11-45` |
| KCP 通道密钥 | `[]byte(salt + verifyKey)` **截断/补 NUL 到 32 字节**，没有任何 KDF | `kcp.go` `kcpBlockCrypt` |
| 每植入端密钥 | **没有**。一个监听器所有 agent 共用同一把帧密钥 | `kcp.go:489`、`listener.go:293-303` |
| 身份 (`VerifyKey`) | 是**标识**不是密钥：拿来 `vkeyIndex[vkey] → clientID`，且用 `client.VerifyKey == vkey` 比较（**非恒定时间**） | `engine.go:146/370` |
| 随机数 | `var _ = rand.Read` —— 导入了但**没接上**（密钥仍来自配置） | `builder.go:597` |
| 降级路径 | 解密失败会回退到"agent transport frame"再退 **明文 JSON**（审计已记） | `listener.go:287-303`、`:450-459` |

**所以它是"每监听器一把共享密钥 + 手工填写 + 可预测默认值 + 弱 KDF + 非恒定时间比较 + 明文回退"**，
和我们现在（全局 `listener.encryption_key` + 4 字节 XOR 混淆）属于**同一类缺陷**，只是它的实现更粗糙。

对我们只有一个结论：**这条路没有可借鉴的东西**，它恰好证明了"固定密钥烘进载荷"是这类项目的通病，
而不是"行业惯例所以我们也行"。要跳出这个坑，只能按 §2.1~2.4 改成"每植入端密钥 + 会话级 ECDH + 帧绑定 + 证书 pin"。

> 顺带一个反面教材清单（我们自己也不能犯）：`"default"` 当默认密钥、MD5 当 KDF、字符串拼接当 KDF、
> `==` 比较密钥、解密失败退明文。这五条在上表里全齐。
## 6. 一句话回答"如何让通讯不被逆向"

**把长期密钥从二进制里彻底删掉**：构建时只放"被服务端公钥密封的、属于这一台的私钥"，
上线时用 ECDH 换出**会话级**密钥（用完即丢），每一帧用 AAD 绑定"会话 + 类型 + 序号"，
传输层用证书 pin 而不是跳过校验。
这样即使别人把你的载荷完整反编译，他拿到的也只是"这台机器的一次性凭据"，
既解不开别人的流量，也冒充不了服务端 —— **这才是"不被逆向"的正解；混淆只是让过程更慢。**
